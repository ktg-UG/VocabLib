### Phase 8 の順序決定

残タスク（Web一覧・編集／ビジュアル刷新／タグ機能）のうち、**タグ機能**を先に選択。
根拠は `memo.txt` に開発者自身が書いた原則。

> スキーマに触るものはUIより先にやるべき
> （画面が増えてからデータ構造を変える方が高くつく）

Web の単語一覧を作ってからタグ列を足すと、画面・型・データ取得を作り直すことになる。

### 確定した仕様

| 論点 | 決定 |
|---|---|
| 個数 | 1単語につき1タグ |
| 持ち方 | `words.tag`（`text not null default ''`）。別テーブルにしない |
| 用途 | 出題の絞り込み / 一覧の分類。タグ別統計はやらない |
| 入力 | 英単語の入力欄に `incorporation #TOEIC` と書く |
| `#` 無しの場合 | 確認フォームの「修正」ボタンから入力 |
| 既存25語 | 全部に `TOEIC` を付ける |

**1語1タグにしたことで設計が大幅に単純化した。** カンマ区切りの分解も、
部分一致の誤ヒット対策（`,TOEIC,` を探す等）も、重複除去も不要になり、
検索は `WHERE tag = ?` で済む。

### 実装中に設計から変えた3点

1. **rumps の落とし穴**: `MenuItem` は最初に子を入れるまでサブメニュー（`_menu`）を
   持たず、`None` のまま。空の状態で `clear()` を呼ぶと落ちる。
   `if len(self.tag_item):` で守り、UIを起動せずサブメニューの構築・再構築を検証した。
2. **「タグが無いときサブメニューを隠す」を撤回**: 項目を動的に足し引きするより、
   常に出して中身を「すべて」だけにする方が単純で壊れにくい。
   代わりに、選択中のタグの単語が0になったら「すべて」に戻す
   （`list_tags()` は語数0のタグを返さないため、放置すると解除できない絞り込みが残る）。
3. **`set_word_tag()` は `synced_at` を NULL にしない**: 既存の更新系メソッドと同じく
   `updated_at` を進めるだけにした。`synced_at IS NULL OR updated_at > synced_at` に
   引っかかるので push される条件は満たす。1つのクラスに2通りのやり方を残さない。

### 進め方を途中で変更した（重要）

デザイントークンと単語一覧を作って見てもらった時点で「判断できない」という
指摘を受けた。実データは25語・回答十数件しかなく、グラフもヒートマップも一覧も
「スカスカ」以外の情報が出てこない。**この状態で配色を変えても評価できない。**

→ `/mock` にダミーデータの画面を用意し、それを見ながら詰める方式に変更。

| 方針 | 理由 |
|---|---|
| 開発時のみ表示（本番は `notFound()`） | fakeデータを本物と見間違える事故を防ぐ |
| 乱数は固定シード | リロードで数字が動くと、デザインの変化かデータの変化か分からない |
| 本番と同じコンポーネント | モックだけ綺麗になっても意味がない |
| サボった週・詰め込んだ週を混ぜる | 均一なデータは現実に起こらない見え方になる |
| 未学習・期限切れ・今週分を全部含める | どれかが0だと、その状態でレイアウトを判断してしまう |

規模: 98語 / 約2,000回答 / 120日分。

### 先に対応: Gemini の 503 で毎回 Ollama に落ちていた件

「課金しているのにGeminiがぜんぜん機能しない」という報告。同じ呼び出しを5回実測した。

```
[1] HTTP 503 UNAVAILABLE（high demand）
[2-5] HTTP 200 成功
```

**503 は課金と無関係にGoogle側の混雑で起き、しかも待たずに即返る。**
それを1回で2段目に落としていたため、体感が「毎回Ollamaに落ちる」になっていた。

- Mac側: 503 / 500 / 429 なら0.7秒後に**1回だけ**再試行してから次の段へ
  （粘りすぎると「LLMが遅い」問題に化けるため）
- Web側: 落ちる先が無いので最大3回
- 判定は例外の**型ではなくメッセージ**で行う（google-genai の例外型はバージョンで変わり、
  型で書くとSDK更新の日に黙ってリトライしなくなる）
- 偽クライアントを注入する回帰テストを4件追加

### Phase 10 の決定事項

| 論点 | 決定 |
|---|---|
| ビルド方法 | **py2app**（rumps公式が推奨。macOS専用でよい） |
| `.env` の場所 | `~/Library/Application Support/VocabLib/.env`（DBと同じ場所） |

**v1 は `datas=[('.env', '.'), ('credentials.json', '.')]` で鍵をバンドルに焼き込んでいた。**
v2 で同じことをすると Gemini のキーに加えて Supabase の `service_role` キーまで
配布物に載る。繰り返さない。

### ビルドで踏んだ3件（いずれも開発中には出ない）

1. **`install_requires is no longer supported`**
   `pyproject.toml` の `dependencies` が setuptools 経由で自動的に
   `install_requires` に入り、py2app がそれを拒否する。
   `parse_config_files` 後に空にする `Distribution` サブクラスで回避。
2. **`ImportError: attempted relative import with no known parent package`**
   py2app は指定スクリプトを `__main__` として直接実行するため、
   `src/main.py` の `from . import config` が壊れる。`launcher.py` を入口にした。
3. **`~/Library/Application Support/VocabLib/.env` に v1 の残骸**（2026-02、Sheets用）
   当初の探索順（Application Support 優先）だと、これがリポジトリの `.env` を
   黙って隠し、**Geminiのキーも同期設定も読めない状態**になった。

### 設計から変えた点: `.env` の探索順を逆にした

上の3番目を踏んで変更した。

```
1. <リポジトリルート>/.env                        ← 開発中
2. ~/Library/Application Support/VocabLib/.env   ← 配布した .app
```

`.app` の `ROOT_DIR` はバンドルの中を指すので1は存在せず、必ず2が使われる。
**どちらの環境でも、その環境の人が置いたファイルが読まれる。**
逆順だと、配布後に `.env` をコピーした時点で2つのファイルが並存し、
「リポジトリ側を直したのに効かない」が起き続ける。

### `packages` に `src` を入れる理由

py2app は既定でコードを zip に固め、**zipに入るのは `.py` だけ**。
`packages` に入れたものはディレクトリのままコピーされる。
外すと `src/db/schema.sql` が同梱されず、起動直後にDBを作れずに落ちる。
