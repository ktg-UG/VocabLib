# 設計書: LLM連携（Phase 3）

- 作成日: 2026-08-15
- 対象機能: F-03 AI例文生成（不正解時）／F-09 単語登録の和訳・品詞オートフィル
- 前提: Phase 1・2 完了済み（テスト37件パス、実機動作確認済み）

---

## 1. このPhaseのゴール

**LLMを3段フォールバックで組み込み、以下2つを動くようにする。**

| 機能                           | いつ動くか                         | 失敗したらどうなるか                                           |
| ------------------------------ | ---------------------------------- | -------------------------------------------------------------- |
| 例文生成（F-03）               | クイズに**不正解した時だけ** | 最終的に`"postpone" means "延期する"` を出す（必ず何か出る） |
| 和訳・品詞オートフィル（F-09） | 単語登録で英単語を入力した直後     | 空欄のまま手入力できる（登録は止まらない）                     |

**どちらも失敗してアプリが止まってはいけない。** LLMはあくまで補助であり、
オフラインでも VocabLib は完全に動く、というのがv2の設計思想（SPEC 1.3）。

### やらないこと（明示）

- **4択の誤答選択肢をLLMで生成すること**
  - 現状は登録済み単語の和訳から取っており、これで十分機能している（Phase 2で確認済み）
  - 出題は5分ごとに発生するため、毎回LLMを呼ぶとレイテンシと無料枠を無駄に消費する
  - 例文（不正解時のみ）とオートフィル（登録時のみ）に限定すれば、呼び出しは「たまに」で済む
  - → SPEC.md の F-04 は「LLM補強は行わない」に確定させる
- Supabase Edge Function 経由でのLLM呼び出し → Phase 4以降（Web側を作る時）
- 発音・複数意味の取得（SPEC 1.3・11節で対象外と確定済み）

## 3. 3段フォールバックの設計

### 3-1. Provider インターフェース（`base.py`）

各LLMの違いを1メソッドに押し込める。

```python
class LLMProvider(Protocol):
    name: str
    def is_available(self) -> bool: ...
    def complete(self, prompt: str) -> str | None: ...
```

- `complete` は**プレーンテキストを返すだけ**。JSON解釈や検証は呼び出し側（`client.py`）がやる。
  こうしておくと、Provider を1つ足すのに他を触らずに済む。
- 例外は Provider の中で握りつぶし、`None` を返す。**上位に例外を投げない。**
  （LLMの失敗は「異常」ではなく「想定内の分岐」なので）

### 3-2. 段の順序

| 段 | Provider            | 使う条件                                      | だいたいの所要 |
| -- | ------------------- | --------------------------------------------- | -------------- |
| 1  | Gemini Flash        | `GEMINI_API_KEY` があり、ネットが生きている | 1〜2秒         |
| 2  | Ollama（gemma2:2b） | localhost:11434 が応答する                    | 3〜10秒        |
| 3  | ローカル生成        | 常に成功する                                  | 即時           |

3段目はLLMではなくただの文字列組み立て（`"word" means "meaning"`）。
**「必ず何か返る」ことを保証する終端**として置く。

### 3-3. `LLMClient`（`client.py`）

```python
class LLMClient:
    def __init__(self, providers: list[LLMProvider] | None = None): ...

    def generate_example_sentence(self, word: str, meaning: str) -> str:
        """必ず文字列を返す（最終段があるため None にならない）"""

    def lookup_word(self, english: str) -> WordInfo | None:
        """和訳と品詞を引く。全段失敗時は None（空欄で手入力させる）"""
```

```python
@dataclass(frozen=True)
class WordInfo:
    japanese: str
    part_of_speech: str | None
```

**`providers` を引数で差し替えられるようにする。** これが重要で、テストでは
ネットにもOllamaにも触らない偽Providerを注入して、フォールバックの順序だけを検証する。

処理の流れ（両メソッド共通）:

```
for provider in providers:
    if not provider.is_available(): continue
    raw = provider.complete(prompt)
    if raw is None: continue
    parsed = 検証・抽出(raw)
    if parsed is None: continue     ← 出力がおかしければ次の段へ
    return parsed
return 最終フォールバック
```

**「呼べたが出力が使い物にならない」場合も次の段に落ちる**のがポイント。
v1は Ollama の出力が不正でも再試行するだけで、別手段に切り替わらなかった。

## 4. v1から移植するもの（`parsing.py`）

v1 の `ollama_client.py` には、**実際にLLMの変な出力に殴られて育った検証ロジック**がある。
ここは作り直さずそのまま持ってくる。純粋関数なのでテストも書ける。

| 関数                                   | 何をするか                                                     | なぜ必要か                                                                                 |
| -------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `extract_example_line(out)`          | 出力から「英文 — 和訳」の行を1つ抜き、区切りを`—` に正規化 | LLMは「例:」「1.」「```」等を勝手に付ける                                                  |
| `sentence_uses_word(sentence, word)` | 英文部分に対象単語が含まれるか検証（語尾変化を許容）           | **単語と無関係な例文が返ることがある**。これを通さないと役に立たない例文が保存される |
| `extract_json(out)`                  | コードフェンスを剥がしてJSONオブジェクトを抜く                 | JSON限定を指示しても説明文を付けてくる                                                     |

`sentence_uses_word` の中身（v1の実装をそのまま使う）:

- 単語を英字トークンに分解し、4文字以上のものを優先
- 各トークンの先頭 `max(4, len-2)` 文字を語幹とみなして部分一致
- → `postpone` に対し `postponed` / `postponing` を許容する

### プロンプトに残す指示

v1のプロンプトにあった以下は**実際に踏んだ罠への対策**なので引き継ぐ。

- 「和訳は必ず自然な**日本語**で書くこと（中国語は絶対に使わない）」
  → 小さいモデルは日本語指示に対して中国語を返すことがある
- 「正解の同義語・言い換えは選ばないこと」（誤答生成用。今回は使わないが記録として残す）
- 「出力は次の1行だけ。番号・説明・引用符は不要」

## 5. 例文生成の組み込み（F-03）

### 5-1. どこに入るか

Phase 2 で `QuizPanel` は不正解時に `words.example_sentence` を表示し、
無ければ「💡 例文はまだありません」を出している。ここを差し替える。

**`QuizPanel` にLLMを持たせない。** パネルは表示するだけにして、
生成の指揮は `menubar.py` が執る。

```python
# panel.py に追加する公開メソッド
def set_example(self, text: str) -> None:
    """例文ラベルを差し替える。パネルが閉じていれば何もしない"""
```

### 5-2. 流れ

```
不正解を選ぶ
   ↓
panel: ボタンを ❌/✅ に着色 → on_answer(False) を呼ぶ
   ↓
menubar._on_answer():
   ① store.record_answer()               ← 同期。数ミリ秒
   ② 例文がキャッシュ済みならここで終了
   ③ 未キャッシュなら:
        panel は「💡 例文を生成中...」を表示済み
        threading.Thread で llm.generate_example_sentence()
   ↓（ワーカースレッド・数秒）
   ④ 生成完了
        callAfter(panel.set_example, text)   ← UI更新はメインスレッド
        store.set_example_sentence(...)      ← 次回から即表示
```

### 5-3. スレッドの規約（Phase 2 で決めた通り）

> **DBアクセス・ネットワークはワーカースレッド。UI操作は必ず `callAfter` でメインスレッドに戻す。**

Phase 2 の時点ではDBが速いので同期呼び出しで済ませていたが、
**Phase 3 でこの規約が実際に必要になる**。LLMは数秒かかるため、
メインスレッドで呼ぶとメニューバー全体が固まる。

生成中にパネルが閉じられるケースがあるので、`set_example` は
`_closed` フラグを見て何もしないようにする（Phase 2 で入れた仕組みを流用）。

## 6. オートフィルの組み込み（F-09）

### 6-1. UX

`rumps.Window` は入力欄が1つしか無いため、**「前の入力結果を次のダイアログの初期値に入れる」**
形でオートフィルを実現する。

```
[1] 「追加する英単語を入力してください」  → postpone
        ↓ LLMに問い合わせ（数秒）
[2] 「和訳を確認・修正してください」      → 初期値: 延期する      ← オートフィル
[3] 「品詞を確認・修正してください」      → 初期値: 動詞          ← オートフィル
        ↓
    store.add_word(english, japanese, part_of_speech)
```

**初期値であって確定値ではない。** ユーザーが上書きできるので、
LLMが間違えても実害がない（SPEC F-09 の「編集可能な下書き」を満たす）。

LLMが失敗したら初期値が空になるだけで、フローは同じ。

### 6-2. 割り切り: 同期呼び出しにする

`rumps.Window` はモーダルでメインスレッドを止めるため、
この流れの中でワーカースレッドを使っても意味がない（どのみち待つ）。

そこで**オートフィルだけは同期呼び出しにし、タイムアウトを短く（5秒）設定する。**
最悪5秒メニューバーが固まるが、ユーザーが自分で「追加」を選んだ直後の
数秒であり、許容できると判断する。

> 将来 `NSPanel` で自前のフォームを作れば非同期にできる。その時に見直す。

## 7. 設定値の追加（`config.py`）

| 変数名                       | 既定値                     | 用途                                 |
| ---------------------------- | -------------------------- | ------------------------------------ |
| `GEMINI_API_KEY`           | （空）                     | 空ならGemini段をスキップする         |
| `GEMINI_MODEL`             | `gemini-2.5-flash`       | 使うモデル                           |
| `OLLAMA_HOST`              | `http://localhost:11434` | ローカルLLM                          |
| `OLLAMA_MODEL`             | `gemma2:2b`              | SPEC 11節で確定済み                  |
| `LLM_TIMEOUT_SECONDS`      | `20`                     | 例文生成用                           |
| `AUTOFILL_TIMEOUT_SECONDS` | `5`                      | オートフィル用（UIを止めるので短く） |

`.env.example` に追記する（`GEMINI_API_KEY` 以外は既に記載済み）。

### APIキーの扱い

- Macアプリからは **Gemini APIを直接叩く**。キーは `.env`（Git除外済み）に置く。
- SPEC 6節にある「Edge Functionに秘匿」は **Web側の話**。ブラウザにキーを置けないため
  Edge Functionを挟む必要があるが、ローカルで動くMacアプリには当てはまらない。
- `.app` 配布する場合はキーがバンドルに入るため、配布時は再考する（今は自分専用なので問題ない）。

## 9. テスト方針

**ネットワークにもOllamaにも触らないテストだけを書く。**

### `tests/test_llm_parsing.py`（純粋関数）

| テスト                        | 内容                                                           |
| ----------------------------- | -------------------------------------------------------------- |
| 「例:」等のマーカーを除去する | `例: He postponed it. — 彼は延期した。` → マーカーが消える |
| 区切りを`—` に正規化する   | `–` や `-` でも同じ結果になる                             |
| コードフェンスを無視する      | `` ``` `` 行を飛ばす                                           |
| 抽出できなければ None         | 区切りが無い出力                                               |
| 語尾変化を許容する            | `postpone` に対し `postponed` `postponing` が真          |
| 無関係な文を弾く              | `The cat sleeps.` に対し `postpone` は偽                   |
| JSONを抽出できる              | 説明文やコードフェンス付きでも抜ける                           |

### `tests/test_llm_client.py`（偽Providerを注入）

| テスト                                             | 内容                              |
| -------------------------------------------------- | --------------------------------- |
| 1段目が成功したら2段目を呼ばない                   | 呼び出し回数を数える              |
| 1段目が None なら2段目に落ちる                     |                                   |
| 1段目が**不正な出力**を返しても2段目に落ちる | v1に無かった挙動。ここが今回の肝  |
| 全段失敗しても例文は必ず返る                       | `"word" means "meaning"` になる |
| 全段失敗したら`lookup_word` は None              | 登録フローを止めないため          |
| `is_available()` が偽のProviderは呼ばれない      | APIキー未設定時にGeminiを飛ばす   |

`src/llm/gemini.py` と `ollama.py` の実通信部分は自動テストしない（手動確認で担保）。

## 10. 完了の定義（DoD）

`uv run pytest` が通ることに加え、以下を手動で確認する。

### LLMなしの状態（最重要）

1. `GEMINI_API_KEY` 未設定 & Ollama停止 で起動する
2. 不正解時に `"postpone" means "延期する"` 形式の例文が出る（アプリが固まらない）
3. 単語登録が空欄オートフィルで最後まで完了する
4. **この状態でPhase 2 の全機能が変わらず動く**（LLM導入で既存機能が壊れていないこと）

### Gemini あり

5. `GEMINI_API_KEY` を設定し、不正解時に自然な例文が数秒で表示される
6. 同じ単語で再度不正解になると、**即座に**例文が出る（キャッシュが効いている）
7. 単語登録で和訳・品詞が初期値として入り、**編集して保存できる**

### Ollama あり（Gemini なし）

8. `GEMINI_API_KEY` を外し Ollama を起動 → 例文が生成される（2段目に落ちている）

### 異常系

9. ネットを切って不正解 → 待たされすぎず、最終的に何らかの例文が出る
10. 例文生成中にパネルを閉じてもエラーにならない

確認結果（成功/失敗）は `development-logs/YYYYMMDD-devlogs.md` に記録する。
