あわせて、実際に使ってみて出た不満のうち**スキーマ変更を伴わないもの**を

#### 7-3 を取り消した理由（2026-08-15 追記）

作業中に開発者から役割分担の原則が示され、SPEC 1.4 として確定した。

> Macアプリは 単語の登録 / 出題 / 統計の数値確認 のみ。
> グラフ・一覧・編集など複雑なUIが要るものはWebに置く。

削除UIはこの原則に反するため、実装済みだったものを取り消した
（`dialogs.prompt_delete_word` と `Store.find_words_by_english` を削除）。

**削除機能は Phase 8 で Web 側に実装する。** その際:

- RLS に UPDATE ポリシーが必要（論理削除は `deleted = true` の更新のため）

- Web に単語一覧ができた時点で、Macの「単語一覧...」も外す
  （機能が一時的に消える期間を作らないため、Phase 7 では残す）

### やらないこと（明示）

- タグ機能 → スキーマ変更を伴うので別Phase
- Webの見た目の作り込み → Phase 8
- Webからの単語登録 → SPEC 1.3 のスコープ変更になるため別途判断

## 2. 一括インポート（7-1）

### 2-1. 使い方

```bash
uv run python -m src.tools.import_words tmp.txt
uv run python -m src.tools.import_words tmp.txt --dry-run   # 登録せず結果だけ見る
```

入力は**1行1単語のテキストファイル**。

```
be indicative of
yield
proximity to
```

- 前後の空白は除去する（実データに末尾スペースがあった）
- 空行と `#` で始まる行は無視する
- 熟語・フレーズもそのまま1エントリとして扱う

### 2-2. 処理

```
各行について:
    1. 既に同じ英単語が登録済みなら skip
    2. LLMClient.lookup_word() で和訳と品詞を取得
    3. 取得できたら store.add_word(english, japanese, part_of_speech)
    4. 取得できなければ skip して、最後に一覧で報告する
```

**取得に失敗した単語を空欄で登録しない。** 和訳の無い単語は出題できず、
4択の選択肢としても使えないため、DBに入れる価値がない。
失敗分は一覧で出して、Macアプリのフォームから手で登録してもらう。

### 2-3. レート制限への配慮

Geminiの無料枠には毎分のリクエスト上限がある。25語を一気に投げると
429 が返り、**Phase 3 のフォールバックが働いてOllamaに落ちる**（動作としては正しいが、
ローカルLLMの方が品質が落ちるので避けたい）。

`--delay`（既定1.0秒）で間隔を空ける。25語なら30秒程度で終わる。

### 2-4. 出力

```
インポート: tmp.txt（25行）

  登録   23語
  skip    1語（登録済み: yield）
  失敗    1語（LLMが和訳を返さなかった: lows take effect）

失敗した単語はメニューバーの「単語を追加...」から手で登録してください。
```

### 2-5. 和訳・品詞を直接指定する書式（2026-08-16 追記）

**きっかけ**: 25語のdry-runで Gemini の無料枠（20リクエスト/日・5/分）を使い切り、
全件が2段目の Ollama（gemma3:4b）に落ちた。その出力を確認したところ品詞の誤りが目立った。

| 単語 | Ollamaの出力 | 正 |
| ---- | ------------ | -- |
| `incorporation` | 組み入れる / **動詞** | 名詞 |
| `resilience` | 回復力 / **形容詞** | 名詞 |
| `unanimously in favor of` | 全員一致して賛成 / **動詞** | 熟語 |
| `barely` | **ほとんど** | かろうじて（逆の意味に読める） |
| `indefinitely` | 永久に | 無期限に |
| `residue` | 残滓 | 残留物 |

品詞の誤りは 7-2（同じ品詞から誤答を選ぶ）を無意味にするため、**放置できない**。

そこで入力ファイルに、LLMを迂回して値をそのまま登録する書き方を足す。

```
yield                          ← 従来どおりLLMが補完する
incorporation, 法人設立, 名詞     ← 書いたとおりに登録（LLMを呼ばない）
yield, 産出する                  ← 品詞は省略できる
```

- 英単語側にカンマを含むフレーズは扱えない（実データに無いので許容する）
- 品詞は `db.store.PARTS_OF_SPEECH` の9種のみ受け付け、外れたら**行番号付きでエラー**にする
  - 表記ゆれ（動詞 / 他動詞 / 【動】…）が1つ混ざると 7-2 が効かなくなるため、
    黙って通さない
- `--delay` はLLMを呼ぶ行の間だけ待つ（レート制限のための待機なので）

**品詞の一覧の置き場所**: これまで `ui/add_word_panel.POS_OPTIONS` にしか無かったが、
`ui` より下の層から import できないため `db/store.py` に `PARTS_OF_SPEECH` として移す。
プルダウンは `[POS_UNSET, *PARTS_OF_SPEECH]` で組み立てる。

### 2-6. 置き場所

`src/tools/import_words.py`。

CLAUDE.md のフォルダ構成に `scripts/` は無く、ソースは `src/` に置く決まりなので、
`src/tools/` を新設して `python -m` で実行できるようにする。

## 3. 同じ品詞から誤答を選ぶ（7-2）

### 3-1. 何が問題か

現状の `get_distractor_meanings()` は品詞を見ずにランダムで和訳を拾う。
その結果、こういう問題が出る。

```
postpone（動詞）
  1. 延期する      ← 正解
  2. りんご        ← 名詞。明らかに違うと分かる
  3. 近接          ← 名詞
  4. 徹底的な      ← 形容詞
```

**品詞が違うだけで消去法が働き、意味を知らなくても正解できてしまう。**
SM-2 が「覚えた」と誤判定する原因になる（SPEC 9 の既知の問題）。

### 3-2. どう直すか

`Store.get_distractor_meanings()` に `part_of_speech` を渡せるようにする。

```python
def get_distractor_meanings(
    self,
    exclude_word_id: str,
    limit: int = 3,
    part_of_speech: str | None = None,
) -> list[str]:
```

1. まず同じ品詞の単語から取る
2. 足りなければ品詞を問わず補充する（**出題できないより、少し易しい方がマシ**）
3. `part_of_speech` が `None`（未設定の単語）なら、従来どおり品詞を問わない

`build_quiz()` が `word.part_of_speech` を渡すだけで、UI側の変更は不要。

### 3-3. 既存データへの影響

Phase 3 より前に登録した単語は `part_of_speech` が NULL のことがある。
その場合は 3 の分岐に落ちるので、**エラーにはならず従来どおり動く**。

インポートで入る単語はLLMが品詞を付けるので、以後は揃っていく。

## 4. 単語の削除UI（7-3）

### 4-1. 何が問題か

`Store.soft_delete_word()` は Phase 1 で実装し、テストも通っている。
**しかし呼び出す画面が存在しない。** 誤登録した単語を消す手段が無く、
一度入れると永久に出題され続ける。

### 4-2. 実装

メニューに「単語を削除...」を追加する。

```
[1] rumps.Window で英単語を入力
        ↓
[2] 該当する単語を検索
        ├─ 0件 → 「見つかりません」
        ├─ 1件 → 確認アラート → soft_delete_word()
        └─ 複数件（run=走る / run=経営する のように同じ綴りで和訳違い）
              → 和訳を並べて、どれを消すか選ばせる
        ↓
[3] 削除後に統計表示を更新
```

`Store` に検索メソッドを1つ足す。

```python
def find_words_by_english(self, english: str) -> list[Word]:
    """英単語の完全一致で検索する（大文字小文字は区別しない）"""
```

> テキスト入力による削除は洗練されていないが、Phase 8 でUIを作り込む際に
> 一覧からの選択に置き換える。**まず「消せない」状態を解消することを優先する。**

### 4-3. 論理削除であること

`soft_delete_word()` は `deleted = 1` を立てるだけで行は残す。
Supabaseにも `deleted = true` が同期され、他端末にも削除が伝わる（墓標）。

回答履歴（`answer_log`）は消さない。過去の統計は保持される。

## 6. 完了の定義（DoD）

`uv run pytest` が通ることに加え、以下を手動で確認する。

### インポート

1. `--dry-run` で登録されず、結果だけが表示される
2. 実行すると単語が登録され、和訳・品詞が入っている
3. 同じファイルを再実行すると全件skipされる（二重登録されない）
4. 失敗した単語が一覧で報告される
5. 同期するとSupabaseにも入り、Webダッシュボードの「登録単語」が増える

### 出題

6. 4択の選択肢が**同じ品詞で揃っている**
7. 品詞が揃わない単語でも出題でき、落ちない
8. 品詞が未設定の単語でも従来どおり出題できる

### 削除

9. 「単語を削除...」で単語を消せる
10. 消した単語が出題されなくなり、単語一覧からも消える
11. 同じ綴りで和訳が違う単語がある場合、どちらを消すか選べる
12. 削除後も統計（過去の回答履歴）が残っている
13. 同期するとWeb側の「登録単語」も減る

確認結果は `development-logs/YYYYMMDD-devlogs.md` に記録する。
